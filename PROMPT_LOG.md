Дополнительные исправления критических багов
**Инструмент:** Claude.ai
### Промпт 1-10
**Промпт:** Корректно ли работает приложение? Нет ли критических багов?
**Результат:** Обнаружено порядка 10 критических багов, после исправления которыз код будет полностью рабочим:
1) Исправление and вместо , в SQL-фильтре — устранение двойного бронирования
Решение: В методе is_table_booked (файл repositories/table_booking_repository.py) разделено сложное условие через and на отдельные аргументы filter: TableBooking.booking_time < end и TableBooking.booking_time >= start. Теперь SQL-запрос формируется корректно, конфликтующие брони обнаруживаются.
2) Полное перекрытие интервалов при проверке брони — ловит случай 18:00 при проверке 19:00
Решение: В том же методе is_table_booked условие пересечения заменено на проверку интервалов: TableBooking.booking_time < check_end и TableBooking.booking_time > check_time - duration. Это гарантирует обнаружение любой брони, даже если её начало ровно совпадает с началом проверяемого интервала.
3) Удаление пользователя с каскадным удалением зависимостей (WorkLog, TableBooking) — устранение IntegrityError
Решение: В UserService.delete_user перед удалением пользователя явно удалены записи из таблиц work_logs и table_bookings через db.query(...).delete(), а также собраны ID заказов до начала их удаления (чтобы избежать ошибок сессии). После этого удалён сам пользователь.
4) Использование UTC вместо локального времени при проверке брони в заказе
Решение: В методе OrderService.create заменён вызов datetime.now() на datetime.now(timezone.utc) для получения текущего времени в UTC. Это устраняет рассинхрон между временем брони (хранится в UTC) и проверяемым временем.
5) Перенос UPDATE из GET-запроса в отдельную логику — снятие блокировок SQLite
Решение: Из метода TableBookingService.get_week_bookings удалено обновление статуса истекших броней (status="expired"). Теперь брони, у которых booking_time < now, просто не показываются в активных, а их статус остаётся "active". Это предотвращает запись в БД при GET-запросе и исключает блокировки при параллельных вызовах.
6) Безопасная обработка user_id в get_current_user_optional — предотвращение 500 ошибки
Решение: В функцию get_current_user_optional (файл dependencies.py) добавлена обработка ValueError при преобразовании user_id в int. Теперь при некорректном формате или отсутствии sub функция возвращает None (а не выбрасывает исключение).
7) Настраиваемый флаг secure для cookie — поддержка HTTP в разработке и HTTPS в продакшене
Решение: В config.py добавлена переменная COOKIE_SECURE: bool = False. В эндпоинте /login при установке cookie используется secure=settings.COOKIE_SECURE. В .env для продакшена можно задать COOKIE_SECURE=true. Теперь при локальном запуске на HTTP cookie принимается браузером.
8) Декоратор @handle_errors для эндпоинта order_status_update — редирект вместо голого JSON
Решение: Над функцией order_status_update (файл orders.py) добавлен декоратор @handle_errors(redirect_url="/pages/orders"). Теперь при возникновении HTTPException пользователь перенаправляется на страницу заказов с сообщением об ошибке вместо получения сырого JSON.
9) (Дополнительно) Аналитика с использованием UTC даты — корректный подсчёт выручки за сегодня
Решение: В AnalyticsService.get_dashboard заменён date.today() на datetime.now(timezone.utc).date(), а фильтр func.date(Order.created_at) == today теперь сравнивает UTC-дату с UTC-датой. Это устраняет ошибку при ненулевом часовом поясе сервера.
